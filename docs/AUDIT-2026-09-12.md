## 1. P0 · 阻断级

### A1. 运行时从未调用 `ContentRegistry.RegisterAll()` → 出货版内容层为空

**证据**
- 全仓库 `grep -rn "RegisterAll" --include=*.cs .`：命中 20 处，**全部在 `Tests/`** 中；非测试引用只有 `ContentRegistry.Years/GenericDayPools/PeerLines` 等静态数据字段。
- 逐个内容类反查：`ContentPrologueMayor.Register()` / `ContentDossierM0.Register()` / … 的唯一调用点是 `ContentRegistry.cs:15-25` 自身。
- 内容类均无静态构造函数（`grep "static Content"` 为空），不存在隐式自注册。
- git 回溯：`git grep -n "RegisterAll" b8e4ff9 -- '*.cs'`（Phase 1 初始提交）同样只有定义、没有运行时调用 → **不是新引入的回归，而是从未接线**。
- `GameBootstrap.Awake`（GameApp.cs:818-826）只做 `ui.Build(...)` + `app.Init(ui)`；`GameApp.Init`（GameApp.cs:78-99）只做事件订阅、`LoadLlm`、`RefreshMenuSaves`。

**后果（Play / 构建产物）**
| 系统 | 表现 |
| --- | --- |
| 序章三幕 | `Flow.Begin` 入队 `mp0/mp1/mp2`，但 `ById` 为空 → `TakeNext` 取不到事件 → 直接落到 `BuildGenericDay`，序章被跳过 |
| 卷宗签批（Phase 5 全部卖点） | `DossierEngine` 注册表空 → `AssignWeek` 装配 0 件 → 案头永远没有卷宗 |
| 年度考核 | `sys_annual_eval`（`md=01-15`）未注册 → 十年没有任何考核 |
| 结局 | `sys_ending`（`date=2036-08-27`）未注册 → **游戏永不结局**，`grade` 永不变化 |
| 口径手册 | `Rulebook` 空 → `Grant` 静默失败 → 口径页/案头提示全空 |
| 新闻栏、时钟链、对上报告链 | 全部未注册（`ContentNews` 仅被 RegisterAll 调用） |
| 仍在工作的部分 | `GenericDayPools / PeerLines / Years` 是静态字段，所以"日常+周评+月结"会一直循环——**看起来像在跑，其实是个空转的壳**，这也是它没被一眼发现的原因 |

**为什么 37/37 全绿**：11 个测试文件每个都自己 `ContentRegistry.RegisterAll()`（共 10 处），覆盖的是模拟层逻辑，**从未覆盖 boot 路径**。测试绿 = 引擎逻辑对，≠ 出货能玩。

**修复（一行级）**
```csharp
// GameApp.Init 首行，或 GameBootstrap.Awake 在 ui.Build 之前
ContentRegistry.RegisterAll();   // _registered 一次性守卫已能防空转/重复注册
```
并补一条**不允许自己调用 RegisterAll** 的启动冒烟测试：
```csharp
Assert.IsTrue(Flow.IsRegistered("mp0"));
Assert.IsTrue(DossierEngine.IsRegistered("dz_t1"));
Assert.IsTrue(Rulebook.IsRegistered("rule_shuzi"));
Assert.IsTrue(Flow.IsRegistered("sys_ending"));
```

### A3. 卷宗总量 62 件、运行时不再补货 → 约第 13 周后案头永久空转

**证据**
- 手写件：`ContentDossierM0`(9) + `ContentDossierY1`(17) = **26 件**（脚本校验）。
- 模板件：`ContentRegistry.cs:22` `DossierGenerator.SeedPool(36, new DateTime(2026,9,1))` = **36 件**，且**在整个进程只调用一次**。
- `SpawnOne` 的调用者只有 `SeedPool` 与 `GeneratorPoolTest`；`AssignWeek` 的 `taken` 排除 `st.dossierFired`，**没有任何补货/回收路径**。
- 周预算 `Math.Max(3, st.weekDossierBudget)` = 每周 5 件；十年 ≈ 520 周。

**后果**：62 ÷ 5 ≈ **12–13 周（约 3 个月）后池子枯竭**，此后每周 `pendingDossierIds` 恒为空 → `HasWork` 恒 false → 卷宗场景消失、合规/效率两把尺冻结、`dossierFired` 不再增长。Phase 5 的核心循环在第一季度之后就不存在了。文档注释 "模板池，防第一年枯竭" 与实际机制直接矛盾。

**修复**：在 `AssignWeek` 末尾按需生成补货，例如
```csharp
while (st.pendingDossierIds.Count < budget)
    DossierEngine.RegisterPool(DossierGenerator.SpawnOne(GameClock.Parse(st.date)));
```
（注意配合 B2：生成件 id 应由存档内计数器派生，而不是进程级 `seq`。）

## 2. P1 · 高危

### B1. 事件与卷宗并存时的输入错配（同一屏两套解释，点击被吞/误签）

**证据**
- `Flow.CurrentScene`（Flow.cs:212-226）：`if (st.queue.Count > 0 || !string.IsNullOrEmpty(st.currentEvent)) return EventScene(st);` → **事件优先显示**。
- `Flow.Choose`（Flow.cs:596-601）：`if (st.activeDossier != null && !resolved && phase == Day) { ChooseDossier(st, idx); return; }` → **卷宗优先处理，且完全不看 queue/currentEvent**。
- `ChooseDossier`（Flow.cs:713-775）的 idx 语义是"翻页/核对/处置"，与事件选项序号无关；`UiRoot.RenderMain`（UiRoot.cs:1663-1691）只把按钮序号 `OnOptionChosen(i)` 回传，**UI 层无任何防护**。

**可复现路径**：周一开始 `ChooseWeekPlan` 自动打开一件卷宗（`Flow.cs:790-797`）；当天任何池事件/时钟事件/`npc_initiative` 入队（工作日 45% 概率）→ 屏上显示事件，但点击走卷宗分支：
- 点 idx=0（若卷宗在第 1 页且多页）→ 变成"下一页 ▶"，**事件答不了**；
- 点 idx=1 → 变成"核 对"，**白扣一次核对次数**；
- 索引落进处置区间 → 用错误的选项序号 **直接签批卷宗**（漏雷照扣合规）。

**修复**：把"屏上是否有事件"抽成一个谓词供两处共用：
```csharp
static bool EventOnScreen(GameState st) =>
    st.queue.Count > 0 || !string.IsNullOrEmpty(st.currentEvent);
// CurrentScene 与 Choose 都先判 EventOnScreen(st)
```
并补一条覆盖"卷宗打开 + 队列有事件"的回归测试（当前测试完全没有这个组合）。

### B2. 卷宗实例丢失 → "继续"是死按钮（软锁）

**证据**
- `DossierEngine.Current`（DossierEngine.cs:135-140）：`RuntimeInstances`（**进程级静态字典**，不随存档）未命中时 `return Clone(st.activeDossier.id)`；若该 id 在当次会话的注册表里不存在 → **返回 null**。
- `DossierScene`（Flow.cs:232-236）在 `d == null` 时给一个只有"继续"的兜底页。
- `ChooseDossier` 首行 `if (d == null || act == null) return;` → **点"继续"什么都不发生**，状态机原地不动。
- 触发条件真实存在：模板件 id = `"dz_g" + seq.ToString("000") + "_" + MMdd`，`seq` 是 `DossierGenerator` 的**进程级静态计数器**；只要先跑过 `GeneratorPoolTest`（其 `SpawnOne` 40 次）再进 Play，`SeedPool(36)` 产出的 id 整体错位 → 存档里记录的 `dz_g001_0901` 之类 id 在新会话根本不存在。

**后果**：读档后主按钮失效，只有"快进"按钮能逃（`FastForward` 内部会 `CloseActive + pendingDossierIds.Clear()`）。玩家观感即"卡死/存档坏了"。

**修复**：`ChooseDossier` 中 `d == null` 时改为 `DossierEngine.CloseActive(st); ` 后继续走正常日推进；并把模板件 id 的计数器存进 `GameState`（存档内），保证跨会话稳定。

### B3. 存档写入乱序 + 快照绕过锁

**证据**
- `GameApp.Save()`（GameApp.cs:735-745）：每次把整份 JSON 丢进 `ThreadPool.QueueUserWorkItem`；`WriteSaveAtomic` 里的 `lock (SaveLock)` 只保证互斥，**不保证 FIFO** → 较早的快照可能晚于较新的快照落盘 → 读档回退。
- `SnapshotSlot`（GameApp.cs:399-424）与 `ResetSave`（GameApp.cs:317-322）**完全不走 `SaveLock`**，与异步自动存档并发写同一路径（`File.Replace`/`File.Move` 竞态）。
- `OnDestroy → FlushSaveSync()`（同步写）同样可能与在途线程写交错，反而让旧数据最后落盘。

**修复**：单一写线程 + 单调序号（只接受 seq 更大的写入）；`SnapshotSlot`/`ResetSave` 纳入同一把锁。

### B4. "核对"实为页号开奖，且部分提示与真相脱节

**证据**
- `DossierEngine.CheckPage`（DossierEngine.cs:146-166）只判 `issue.pageRef == act.page`，**与玩家是否推理无关**；点"核对"即开奖。
- `DossierGenerator.SpawnOne`：只有 `seq % 3 == 0` 才埋"合计差 7"的数字雷，`seq % 3 != 0 && seq % 2 != 0`（约 1/6）的件**完全没有雷**。
- 模板 2（省交办，DossierGenerator.cs:250-292）`detectHint = "完成整改数是否大于发现问题数"`，但 `n2 = rng.Next(3, n1 + 5)`、`sum = n1 + n2 + n3` → **恒有 n2 < sum**，该矛盾在数据上永不出现；玩家照提示推理永远找不到，点"核对"却能命中 → 提示与真相不一致（叙事欺骗）。
- 手写件通用风险：`AssignWeek`/`Register` **没有任何 `pageRef ≤ pages.Count` 校验**，模板作者一改就会出现"永远查不出的雷"。当前 26 件经脚本校验全部自洽（见附录）。

**修复**：为每条 detectHint 绑定**真实存在**的数值矛盾；在 `DossierEngine.Register` 里加自检（越界 pageRef、未知 ruleKey 直接抛/日志）。

## 3. P2 · 中危

### C1. `Flow.CloneEffects` 浅拷贝 4 个记录对象 → 档案记录别名污染
`CloneEffects`（Flow.cs:1391-1410）把 `task/document/integrity/commend` **直接传引用**。`DossierGenerator.SpawnOne` 对模板效果做 CloneEffects，模板里的 `integrity = new IntegrityRecord{...}`（如"配合省督查"灰区选项）被所有生成副本共享同一对象；`ApplyEffects` 会改写 `e.integrity.date` 并 add 进 `st.integrity` → 多条合规记录指向同一对象、最后一条的日期/内容覆盖全部，**程序合规档案失真**（而 integrity 是考核/监察线的数据基础）。`task` 侧目前只因 TaskGenerator 逐个 new 而未触发，机制上仍是雷。→ 深拷贝这 4 个字段。

### C2. `MiniJson` 非线程安全
`Llm.cs:398` `private static int pos;` 每次 `Parse` 重置，**静态可变状态**。当前调用都在主线程（UnityWebRequest 回调在主线程泵），但一旦把解析挪到后台线程或两处解析交错即静默错乱。→ 改成实例化解析器。

### C3. `LlamaServer.starting` 永不复位
`starting` 只在 `EnsureRunning` 正常走完时复位（LlamaServer.cs:76-160）。若该协程因宿主对象销毁/场景切换被中断，`starting` 永久为 true → 之后每次调用都进分支③，白等最多 240s 才失败，"自动拉起"永久失效。→ 加时间戳超时（如 startedAt + 300s 视为失效）或 try/finally 语义。

### C4. `RenderMain` 的签名早退吞掉"摊开口径"刷新
`SceneSig`（UiRoot.cs:1613-1622）只含 `kind/title/paras.Count/options.Count/前2段/首选项/docNo`；换口径只改第 3 段（案头提示行）→ 签名不变 → `RenderMain` 早退（UiRoot.cs:1626-1628）。`GameApp.OpenRule` 里那次"刷新案头提示"的 `RenderMain` 被吞掉 → 玩家摊开新口径后正文提示不更新，须翻页才可见。→ 签名纳入全部 paras（或至少纳入 deskHint 行）。

### C5. API key 明文存储 + 明文回显
`LoadLlm/SaveLlm` 走 `PlayerPrefs` 明文 JSON（key `starstate_llm_cfg3`，GameApp.cs:104-121）；`UiRoot.SetLlmConfig` 把 `cfg.apiKey` 直接写进 InputField（UiRoot.cs:1534），而 `MakeSettingsInput`（UiRoot.cs:1459-1489）**未设 `contentType = Password`**，全仓库 grep 无 `password` → 设置页明文显示密钥。→ 设 Password 类型，至少不回显。

### C6. 测试给出的是假信心（与 A1 联动）
- 11 个 fixture 全部自己调 `RegisterAll()` → 掩盖了运行时不注册（A1）。
- `ContentRegistry._registered` 是一次性守卫：`GeneratorPoolTest` 先跑会 `DossierEngine.Clear()`，之后所有 `RegisterAll()` 变成空操作，后续用例的内容可见性**取决于执行顺序**（测试隔离缺陷）。
- `GrowthSmokeTest` 断言硬编码 `56/62/61/50/55`（Golden 值），任何平衡微调即红（脆）。
- 十年冒烟/平衡测试依赖**未播种**的 `Flow.Rng`（`new Random()`）+ 20 万次循环 → 存在随机失败风险；`TenYearSmokeTest` 的 `evals >= 9` 实际只证明约 6 次真实考核（`State.NewGame` 已预置 2023-2025 三条）。
- 测试完全缺失：事件+卷宗并存（B1）、读档后 `RuntimeInstances` 丢失（B2）、存档乱序（B3）、时钟满格跨年、季节档期。
- `tools/check-compile.sh`：**不编译 Tests 程序集**（注释"由 Unity batchmode 编译"）→ 测试代码语法错误不进门禁；无 `-warnaserror`；硬编码 `D:/pro/unity`、`E:/Starstate` 与 PackageCache 版本号（`com.unity.ugui@1.0.0`、`nunit@1.0.6`），换机器/升包即断。
- 文档数字互斥：`README.md:5` "37/37"、`README.md:13` "2026-09-19，EditMode 23/23"、`README.md:57` "EditMode 17 项"（同一文件三个数）；`docs/HANDOFF.md:16` "30 Passed / 5 Skipped"；`AGENTS.md:22` "37/37"；`changelog/PHASE-5.md:5` "37/37"。实际 `[Test]` 总数 = 37、无 `[Ignore]` → 只有 changelog/AGENTS/README 首行是对的。

### C7. Phase 1–4 科员线残留污染市长线（内容一致性）

## 4. 值得肯定的设计（审计中的正面发现）

1. **分层纪律真实有效**：`Core/` 不依赖 UnityEngine，`check-compile.sh` 第 2 步单独编译 Core 可作证；模拟核心理论可移植、可测试。
2. **内容层数据自洽**：脚本校验 26 件手写卷宗的 `pageRef ≤ pages.Count`、`ruleKey` 全部已注册、dossier id 无重复、每件都有处置选项——**零问题**（见附录）。
3. **LLM 层的防御设计到位**：模型只产文本/情绪分类，数值效果走 `LlmGameplay` 白名单；`Sanitize` 对长度/mood 枚举/空数组做了归一化；解析全程 try-catch + `ExtractFirstJson` 容错；失败一律回退内置台词。**提示词注入的实际危害被压到"文本难看"级别**（玩家可以把名字写进 prompt，但拿不到数值收益）。
4. **效果表克隆意识**（`CloneEffects`）方向正确——只是漏了 4 个记录字段（C1）。
5. **工程纪律**：`.meta` 保护、Boot 场景零脚本（`RuntimeInitializeOnLoadMethod` 自举）、存档原子替换 + `saveVersion` 门槛、`fired` 日志裁剪、记忆条数上限——长线存档的防膨胀考虑得比同类小项目细。
6. **可重现性局部可控**：DossierEngine/生成器用固定种子，只有 `Flow.Rng` 未播种（这也是测试脆弱性来源，见 C6）。
